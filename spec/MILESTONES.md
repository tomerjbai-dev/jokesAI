# MILESTONES — בדיחומט

**מסמכי מקור:** `PRD.md`, `ARCHITECTURE.md`, `DESIGN.md`  
**פלטפורמה:** Mobile First PWA · React + TypeScript + Vite · Vercel Functions · GPT-5  
**עיקרון מנחה:** פיתוח ב-Vertical Slices, בדיקה ואישור של כל Milestone לפני מעבר לבא.

## כללי ביצוע הפיתוח — Development Execution Rules

1. **חובה לפתח את ה-Milestones לפי הסדר המוגדר במסמך.** אין לדלג קדימה או להתחיל יכולות השייכות ל-Milestone הבא.
2. בסיום **כל Milestone יש לעצור את הפיתוח**, להציג למשתמש מה עובד בפועל, היכן ניתן לבדוק אותו, ואת תוצאות הבדיקות מול כל סעיף ב-Definition of Done. יש לציין במפורש בדיקות שלא עברו ומגבלות ידועות.
3. **אין להתחיל את ה-Milestone הבא ללא אישור מפורש של המשתמש.** תיקונים הנחוצים לעמידה ב-Definition of Done שייכים ל-Milestone הנוכחי.
4. `PRD.md` קובע אילו יכולות מותר לממש; `ARCHITECTURE.md` קובע את המימוש הטכני; `DESIGN.md` קובע את השפה החזותית. רכיבים המופיעים בתמונות בלבד, כגון היסטוריה, קטגוריות, העתקה, לייקים, תפריט ניווט ומסך מכסות נפרד, **אינם מאושרים ל-MVP**.
5. אין Database, Redis או Authentication. מכסות ו-Circuit Breaker ב-Vercel הם **Best Effort**, לא אכיפה גלובלית קשיחה; אין לכתוב בדיקות או הודעות המציגות אותם כמובטחים.
6. יש להריץ בדיקות אוטומטיות רלוונטיות ובדיקת שימוש ידנית במובייל בכל שלב. אין להכניס Secrets ל-Git או ל-Frontend. אין לפרסם ל-Production ללא אישור המשתמש.

## Milestone 1 — בסיס אפליקציה וכניסה מותנית בגיל ✅

**מטרה:** להעמיד אפליקציית Web עובדת, ניתנת לבדיקה, עם מסלול הכניסה המאושר ועיצוב הבסיס.

**מה יש לממש:**
- Git Repository ב-GitHub; פרויקט React + TypeScript + Vite, תצורת RTL ועברית, Heebo ו-CSS Variables לפי `DESIGN.md`.
- מסך הצהרת גיל 18+, אישור ושמירתו ב-Local Storage; מסך חסימה למי שאינו מאשר, עם חזרה להצהרה.
- מסך פתיחה ראשי: מותג `בדיחומט`, `על מה צוחקים היום? 😂`, הנחיה קצרה, שדה נושא וכפתור `צור בדיחה` בעיצוב המוסכם. בשלב זה אין יצירת בדיחה אמיתית; אין להציג תוצאה מדומה כהצלחה.
- בדיקות בסיסיות לזרימת גיל ולמבנה המסכים; Build תקין.

**תוצר מצופה:** אפשר לפתוח את האפליקציה בטלפון, לאשר גיל ולהגיע למסך הראשי; ללא אישור אי אפשר להשתמש בה.

**Definition of Done:**
- [ ] `npm run build` ובדיקות הפרויקט עוברים ללא שגיאות TypeScript.
- [ ] ביקור ראשון מציג הצהרת גיל; אישור מאפשר כניסה; אי-אישור מציג חסימה והחזרה להצהרה.
- [ ] רענון לאחר אישור גיל אינו מחייב אישור מחדש; מחיקת נתוני הדפדפן מחזירה את ההצהרה.
- [ ] התצוגה בעברית, RTL, Mobile First, ובה צבעים, טיפוגרפיה ורכיבי UI תואמים ל-`DESIGN.md`.
- [ ] אין מסכים או פעולות שלא אושרו ב-PRD.

## Milestone 2 — יצירת בדיחה מקצה לקצה ✅

**מטרה:** לאפשר את הפעולה המרכזית של המוצר: הזנת נושא וקבלת בדיחה אמיתית בעברית.

**מה יש לממש:**
- `POST /api/jokes` ב-Vercel Functions עם OpenAI SDK ו-Responses API, במודל שנקרא מ-`OPENAI_MODEL` (ברירת מחדל `gpt-5`), באמצעות `OPENAI_API_KEY` בצד השרת בלבד.
- תשובת המודל במבנה קבוע (`{ status: "joke" | "refused", joke }`), `reasoning.effort` נמוך ומגבלת אורך פלט שמשאירה מקום לחשיבה, לפי `ARCHITECTURE.md` §2.6.
- אימות קלט: עד 100 תווים; שדה ריק לחלוטין מייצר בדיחה כללית; רווחים בלבד מציגים `רווחים זה נחמד, אבל תנו לנו נושא אמיתי 😅` ללא בקשת API.
- הפעלה באמצעות הכפתור או Enter/מקש הפעולה במובייל; בדיחה בעברית באורך 1–3 משפטים, ללא כותרת נושא.
- הצגת בדיחה אחת בכרטיס, החלפתה לאחר הצלחה, שמירת הנושא בשדה, ושליחת הבדיחה האחרונה כהקשר למניעת חזרה מיידית ככל האפשר.
- מצבי טעינה: `ממציאים לכם בדיחה...`, נעילת השדה והכפתור, השארת בדיחה קיימת עד להצלחת הבקשה.
- פריסת המסך לאחר הצגת בדיחה לפי `DESIGN.md` §1.3: הבדיחה מעל שדה הנושא, והכפתור מתחלף ל-`בדיחה חדשה`.
- הרצה מקומית עם `vercel dev` (ראה `ARCHITECTURE.md` §2.10): המשתמש יוצר חשבון Vercel ומתחבר, לפי הנחיה צעד אחר צעד, ומוסיף את `OPENAI_API_KEY` ל-`.env`. עדכון "פקודות הרצה" ב-`CLAUDE.md`.

**תוצר מצופה:** משתמש מאושר גיל יכול ליצור בדיחה אמיתית, להחליף נושא או לקבל בדיחה נוספת באותו נושא.

**Definition of Done:**
- [ ] בקשה עם נושא בעברית או בשפה אחרת מחזירה בדיחה בעברית בלבד, בת 1–3 משפטים.
- [ ] שדה ריק מייצר בדיחה כללית; רווחים בלבד נחסמים ללא קריאת OpenAI; קלט מעל 100 תווים אינו נשלח.
- [ ] לחיצה ו-Enter מפעילים את אותה פעולה; בזמן טעינה אין בקשות כפולות והבדיחה הקודמת נשארת מוצגת.
- [ ] הצלחה מחליפה רק את הבדיחה הקודמת; הנושא נשמר עד שהמשתמש משנה אותו.
- [ ] ה-API Key אינו מופיע בקוד לקוח, ב-Build או בתשובות API.
- [ ] בדיקות Validation וזרימת UI עוברות, ונבדקה יצירה אמיתית בסביבת Development/Preview.

## Milestone 3 — תקלות, ביטול בקשות ושימוש ללא חיבור ✅

**מטרה:** להפוך את זרימת יצירת הבדיחה לשימושית גם בעת כשל, סירוב תוכן או אובדן רשת.

**מה יש לממש:**
- Timeout: 28 שניות בשרת ורשת ביטחון של 35 שניות בלקוח (`ARCHITECTURE.md` §1.2 סעיף 7), טיפול בכשלי API, תשובה ריקה או לא תקינה, וסירוב תוכן (זיהוי לפי `status: "refused"` בתשובה המובנית); ההודעות לפי טבלת נוסחי השגיאה ב-PRD (FR-05), ללא בדיחה חלופית אוטומטית.
- ניסיון חוזר ידני בלבד; שימור הנושא והבדיחה הקודמת בכל כשל.
- `AbortController` וניסיון ביטול בקשה בעת רענון, ניווט החוצה או סגירה, בהתאם למגבלות הדפדפן ו-Vercel.
- Web App Manifest, Service Worker באמצעות `vite-plugin-pwa`, Cache של App Shell ומסך Offline עם `אין חיבור לאינטרנט. בדקו את החיבור ונסו שוב.` וכפתור `נסו שוב`. המסך מוצג רק כשהמכשיר מדווח שאין רשת, וחזרת החיבור מחזירה למסך הקודם (`DESIGN.md` §1.5).
- אייקון האפליקציה לפי `DESIGN.md` §2.6 (192, 512, maskable) ועדכון ה-favicon; הצגת האייקון למשתמש לאישור.
- אין Cache של בקשות API או תוכן בדיחות; התקנה באמצעות אפשרות הדפדפן בלבד, ללא Prompt התקנה יזום.

**תוצר מצופה:** האפליקציה מגיבה באופן ברור לכשלי שירות, ניתוק ורענון, ומסך Offline זמין גם ללא רשת.

**Definition of Done:**
- [ ] כשל API, Timeout, ניתוק באמצע בקשה וסירוב תוכן מוצגים בנוסחים שבטבלת FR-05 ב-PRD; אין יצירה חוזרת אוטומטית.
- [ ] לאחר כשל נשמרים הנושא והבדיחה הקודמת; ניתן לנסות שוב ידנית.
- [ ] בקשה שהמודל לא עונה עליה מסתיימת כ-30 שניות אחרי השליחה עם הודעת Timeout; אם השרת לא עונה כלל, הלקוח מפסיק לחכות אחרי 35 שניות.
- [ ] רענון/סגירה מפעילים ניסיון ביטול; לא נטען שניתן לבטל בוודאות קריאת API שכבר התחילה.
- [ ] אחרי טעינה ראשונה ברשת, ניתוק הרשת מציג מסך Offline מתוך ה-PWA; `נסו שוב` או חזרת החיבור מחזירים למסך הקודם עם הנושא והבדיחה.
- [ ] כשל רשת של בקשה בודדת (כשהמכשיר מדווח על חיבור) מציג הודעת "החיבור נקטע" במסך הראשי, ולא את מסך ה-Offline.
- [ ] Manifest כולל אייקונים 192/512 ו-maskable לפי `DESIGN.md` §2.6, והמשתמש אישר את האייקון.
- [ ] האפליקציה ניתנת להתקנה דרך הדפדפן; אין כפתור התקנה ואין Cache של בדיחות או `/api/*`.

## Milestone 4 — מכסות שימוש, Rate Limiting והגנות שירות ✅

**מטרה:** להציג יתרה אישית ולהפעיל את מנגנוני הגבלת השימוש וההגנה על GPT-5, בהתאם לפשרת ה-Best Effort המאושרת.

**מה יש לממש:**
- `GET /api/status`, Cookie חתום עם מזהה אנונימי ומונה אישי משוער, ומונים זמניים לכל Vercel Function Instance; איפוס לפי `Asia/Jerusalem` בחצות, כולל שעון קיץ.
- ערכי ברירת מחדל: 20 בדיחות מוצלחות למזהה ליום, 100 הצלחות גלובליות משוערות ליום, 5 בקשות בדקה (נספר גם לפי מזהה ה-Cookie וגם לפי כתובת IP, בזיכרון בלבד); הצגת יתרה אישית במסך הראשי ועדכונה אחרי הצלחה.
- הודעות והשבתת יצירה כשהמגבלה מזוהה: `נגמרו הבדיחות להיום! חזרו מחר לעוד צחוקים 😄`; `הקומיקאי שלנו סיים להיום 🎤😴 נגמרו הבדיחות, נתראה מחר!`; `רגע, גם לקומיקאי מגיע לנשום 😅` עם Countdown.
- Circuit Breaker מקומי: 5 שגיאות API רצופות, השהיה של 2 דקות, ניסיון בדיקה מבוקר וחזרה לפעילות לאחר הצלחה.
- Configuration ב-Backend ללא שינוי קוד: מכסות, Rate Limiting, Timeout וספי Circuit Breaker. בדיחה נספרת ברגע שהשרת יצר אותה בהצלחה; Validation, שגיאות וסירובים אינם נספרים. אין מנגנון אישור קבלה מהלקוח.

**תוצר מצופה:** המשתמש רואה יתרה משוערת והודעות הגבלה; ה-Backend מפעיל הגנות Best Effort ללא Database.

**Definition of Done:**
- [ ] היתרה האישית מופיעה ומצטמצמת אחרי יצירה מוצלחת באותו דפדפן; ביקור חוזר משתמש ב-Cookie חתום.
- [ ] בקשות כושלות וסירובי תוכן אינם נספרים כהצלחות; ביטול בקשה מטופל כ-Best Effort ולא כהבטחת Exactly-Once.
- [ ] המונים המקומיים מתחלפים ביום חדש לפי שעון ישראל; נבדקים גם תאריכים סביב מעבר שעון קיץ/חורף.
- [ ] בבדיקות מבוקרות של אותו Instance מופיעות הודעות מכסה, השבתת כפתור, Rate Limiting ו-Countdown.
- [ ] Rate Limiting נשאר בתוקף גם אחרי מחיקת ה-Cookie (הגבלה לפי IP), וכתובת ה-IP אינה מופיעה בלוגים.
- [ ] בדיקות מדמות 5 שגיאות API רצופות, המתנה של 120 שניות ו-Probe יחיד באותו Instance.
- [ ] שינוי ערכי Configuration בסביבת בדיקה משפיע ללא שינוי קוד.
- [ ] בדיקת מקביליות/Instances מתעדת במפורש שייתכנו חריגות מהמכסות וש-Circuit Breaker אינו גלובלי; **אין לטעון לאכיפה קשיחה**.

## Milestone 5 — השלמת עיצוב, פרטיות וניטור

**מטרה:** להביא את היכולות העובדות לרמת גימור אחידה, בטוחה ונוחה לשימוש במובייל.

**מה יש לממש:**
- התאמה סופית של המסכים המאושרים ל-`DESIGN.md`: Heebo, צבעי אדום/צהוב/קרם, Radius, Spacing, Shadows, טיפוגרפיה, אייקונים ורקע עדין בהתאם לרפרנסים.
- התאמות מצבי Loading, Disabled, Focus, הודעות שגיאה, מכסות ו-Offline לאותה מערכת עיצוב; RTL תקין וטקסטים בעברית.
- אבטחה: בדיקת Origin ו-Content-Type, הגבלת Body, אימות Cookie, Headers, הצגת פלט AI כטקסט ולא HTML.
- Structured Logs ונתוני תפעול בסיסיים: כמות בקשות, שגיאות API, Latency והפעלת Circuit Breaker; ללא נושאים, בדיחות או מזהים אישיים בלוגים הייעודיים.
- אימות שבפתיחה מחדש הנושא והבדיחה מתאפסים, אך אישור הגיל והמזהה האנונימי נשמרים בדפדפן כל עוד לא נמחקו.

**תוצר מצופה:** ממשק מגובש התואם ל-Style Guide ול-Mockups עבור **המסכים המאושרים בלבד**, עם אבטחה וניטור בסיסיים.

**Definition of Done:**
- [ ] מסכי אישור גיל, חסימה, ראשי ו-Offline נבדקו במכשיר מובייל או ב-Viewport מובייל; אין גלילה אופקית או חיתוך טקסט משמעותי.
- [ ] גופנים, צבעי HEX, כפתורים, שדות, כרטיסים, מרווחים והיררכיית טקסט תואמים ל-`DESIGN.md`.
- [ ] כל הודעות הממשק בעברית, RTL תקין, Focus גלוי, ניגודיות קריאה וכיבוד `prefers-reduced-motion`.
- [ ] בדיקות אבטחה מוודאות דחיית קלט חריג/Origin לא מאושר, Cookie מזויף, ושפלט AI אינו מוזרק כ-HTML.
- [ ] לוגים תפעוליים קיימים ללא שמירת נושאים, בדיחות, Cookies גולמיים או מזהים אישיים.
- [ ] פתיחה מחדש מאפסת נושא ובדיחה, אך לא אישור גיל או Cookie תקין.
- [ ] אין מימוש של היסטוריה, קטגוריות, לייקים, העתקה, תפריט או מסכי מידע שנוספו להמחשות בלבד.

## Milestone 6 — בדיקות קבלה ופריסה ל-Production

**מטרה:** לפרסם MVP יציב ב-Vercel, עם תהליך עדכון אוטומטי ומגבלות השירות מתועדות.

**מה יש לממש:**
- חיבור GitHub Repository ל-Vercel Project אחד; Preview מכל דחיפה לענף `develop`, ו-Production מענף `main` בלבד, שמתעדכן רק בפקודת "פרסם לאוויר" (`CLAUDE.md`).
- Build ו-TypeScript checks ב-CI (GitHub Actions) על כל דחיפה ל-`develop`; הגדרות Routing ל-`/api/*` ול-SPA, ו-Secrets נפרדים ל-Preview ול-Production.
- בדיקת משך Function ביחס ל-Timeout של 30 שניות; הגדרת משתני סביבה (כולל `OPENAI_MODEL`); הגדרת מגבלת התקציב המחמירה ביותר שזמינה בפרויקט OpenAI, שהיא ההגנה העיקרית על העלות, ובדיקה אם היא עוצרת בקשות או רק מתריעה.
- בדיקות End-to-End על Preview ולאחר אישור גם על Production: אישור גיל, יצירה, נושא ריק, Validation, הודעות, מכסות Best Effort, Offline, PWA ופתיחה מחדש.
- אימות שאין Secrets ב-Git או ב-Bundle ושאין Database/Redis או שירותים לא מאושרים.

**תוצר מצופה:** כתובת Vercel חיה למוצר המלא, עם Deployment אוטומטי מ-GitHub ומסלול בדיקה ברור לגרסאות חדשות.

**Definition of Done:**
